# Git Merge Conflicts, Rebase, Stash & Detached HEAD — A Comprehensive Guide

## Executive Summary

Git merge conflicts arise when two branches modify the same lines in a file and Git cannot automatically reconcile the differences. Understanding how to read conflict markers, use `git rebase` for clean linear histories, leverage `git stash` for temporarily shelving work, and handle the "detached HEAD" state are foundational skills for any developer working with Git. This guide covers each concept with practical commands and examples drawn from the official Git documentation and Atlassian's tutorials.

---

## 1. Merge Conflicts: Why They Happen and How to Resolve Them

### What Causes a Merge Conflict?

A merge conflict occurs when two branches diverge and both modify the same area of a file in different ways. Git uses a **3-way merge algorithm** — it looks at the common ancestor and both branch tips — but when competing changes exist, it cannot choose one side over the other and stops the merge [1][3].

There are two failure scenarios [3]:

| Failure Type | Error Message | Cause | Fix |
|---|---|---|---|
| **Failure to start** | `Entry '<file>' not uptodate. Cannot merge.` | Local pending (uncommitted) changes conflict with the incoming merge | Stash or commit your local changes first |
| **Failure during merge** | `CONFLICT (content): Merge conflict in <file>` | Both branches edited the same lines differently | Resolve conflict markers manually |

### Conflict Markers Explained

When a conflict occurs, Git inserts special markers directly into the file [1][3]:

```
<<<<<<< HEAD
this is some content to mess with
content to append
=======
totally different content to merge later
>>>>>>> new_branch_to_merge_later
```

- **`<<<<<<< HEAD`** — Beginnings of *your* current branch's version
- **`=======`** — The divider between the two versions
- **`>>>>>>> branch_name`** — End of the *incoming* branch's version

> **Pro tip:** Set `merge.conflictStyle` to `diff3` or `zdiff3` to add a `|||||||` marker showing the original base state, which makes understanding both sides' changes much easier [1].

### Step-by-Step Resolution

1. **Open the conflicted file(s)** — `git status` shows which files have conflicts (listed as `both modified:`) [3]
2. **Edit the file** — Decide which code to keep, remove the conflict markers, and save the desired final content
3. **Stage the resolved file** — `git add <filename>`
4. **Complete the merge** — `git merge --continue` (or simply `git commit`)

### Useful Commands During Conflicts

- **`git merge --abort`** — Cancel the merge entirely and restore your pre-merge state [1][3]
- **`git log --merge`** — Show only the commits causing the conflict [3]
- **`git diff`** — Inspect differences between states to understand the conflict [3]
- **`git reset --mixed`** — Undo changes to the working directory and staging area if the merge fails to start [3]

### Alternative Merge Strategies

| Option | Effect |
|---|---|
| `--no-commit` | Performs the merge but stops before the final commit for inspection |
| `--squash` | Merges all changes into your working tree without creating a merge commit |
| `-s ours` | Completely discards the incoming branch's changes, keeping only yours |

## 2. Git Rebase: Rewriting History for a Clean Timeline

### What Rebase Does

`git rebase` takes your branch's commits and **replays them one by one** on top of another base tip — conceptually similar to running `git cherry-pick` for each commit [2]. This "catches up" your feature branch with the target branch.

```
# Before rebase: feature branched off an older commit on main
    A---B---C  (main)
         \
          D---E  (feature)

# After `git rebase main` on the feature branch:
    A---B---C
             \
              D'---E'  (feature, rebased)
```

### Handling Conflicts During Rebase

Since rebase replays commits individually, conflicts are resolved one commit at a time [2]:

```bash
# 1. See what's conflicting
git diff

# 2. Edit the file to resolve conflict markers, then stage it
git add <filename>

# 3. Continue to the next commit
git rebase --continue

# Alternatively: skip this commit entirely
git rebase --skip

# Or: abort and return to your original branch state
git rebase --abort
```

### Interactive Rebase (`git rebase -i`)

Interactive rebase opens a **"todo list"** of your commits where you can reorder, edit, or combine them [2][4]:

```bash
git rebase -i HEAD~3
```

This opens an editor showing your last 3 commits. Change `pick` to:
- **`squash`** (or `s`) — combine this commit into the previous one
- **`fixup`** (or `f`) — like squash but discards the commit message
- **`reword`** (or `r`) — edit the commit message
- **`edit`** (or `e`) — pause to amend the commit
- **`drop`** (or `d`) — remove the commit entirely

Use `--autosquash` to automatically arrange commits marked with `squash!` or `fixup!` prefixes next to their targets [2].

### The `--onto` Option: Transplanting Branches

```bash
# Move 'topic' so it appears to have branched off 'master' instead of 'next'
git rebase --onto master next topic
```

### Rebase vs. Merge: The Golden Rule

| | **Merge** | **Rebase** |
|---|---|---|
| **Mechanism** | Creates a merge commit tying both histories | Re-writes history by replaying commits |
| **History** | Preserves full context (who merged what, when) | Creates a perfectly linear history |
| **Safety** | Non-destructive | Re-writes commit SHAs (new commits) |
| **Best for** | Public branches, pull requests | Private/local feature branches |

**The Golden Rule of Rebasing:** *Never rebase public branches* (like `main`). Rebase creates new commit SHAs. If you force-push a rebased public branch, it will diverge from your teammates' repositories, causing catastrophic confusion. If anyone else is looking at the branch, use `git merge` instead [4].

**Practical workflow for integrating a feature:**
1. On your feature branch: `git rebase main` (clean up history)
2. Switch to main: `git checkout main`
3. Fast-forward merge: `git merge feature` (results in a clean, linear main history)

## 3. Git Stash: Shelving Work Temporarily

### What Stash Does

`git stash` saves your local modifications (both staged and unstaged) and reverts the working directory to match `HEAD`. This is essential when you need to switch branches, pull updates, or perform a merge/rebase but aren't ready to commit [5].

### Core Commands with Examples

```bash
# Save all current changes with a descriptive label
git stash push -m "work-in-progress on login feature"

# Save only staged changes
git stash push --staged

# Save unstaged changes but keep staged files in working directory
git stash push --keep-index

# List all stashes
git stash list
# Output:
# stash@{0}: On main: work-in-progress on login feature
# stash@{1}: WIP on main: abc1234 some previous work

# Reapply a specific stash WITHOUT removing it from the list
git stash apply stash@{1}

# Reapply the most recent stash AND remove it from the list
git stash pop

# Delete a specific stash entry
git stash drop stash@{0}
```

### Stash and Merge Conflicts

When `git stash pop` or `git stash apply` causes merge conflicts (because your working tree has changed since the stash was created), **the stash is NOT removed from the stash list**. You must:
1. Resolve the conflicts manually
2. Run `git stash drop` to remove it afterward [5]

**Advanced trick:** If applying a stash fails due to complex conflicts, use `git stash branch <branchname>`. This creates a new branch starting from the exact commit where the stash was originally created, allowing it to be applied cleanly with zero conflicts [5].

### Autostash

Both `git merge` and `git rebase` support the `--autostash` flag, which automatically stashes your dirty working tree before the operation and reapplies it afterward [2][5]:

```bash
git rebase --autostash main
git merge --autostash feature
```

## 4. Detached HEAD State: What It Is and How to Bypass It

### What "Detached HEAD" Means

In Git, `HEAD` is a pointer that normally references a **branch name** (e.g., `ref: refs/heads/main`), which in turn points to a specific commit. A **detached HEAD** means `HEAD` points directly to a commit SHA-1 hash instead of a branch name [6][7].

### How It Happens

| Action | Command | Why It Detaches |
|---|---|---|
| Check out a commit hash | `git checkout 14ko3` | You're on a raw commit, not a branch |
| Check out a tag | `git checkout v1.0.1` | Tags are static; they don't update with new commits |
| Check out a remote branch | `git checkout origin/master` | Remote branches live under `refs/remotes/`, not local branches |

Note: Even if the commit you check out happens to be the tip of your main branch, you're still detached because you used the SHA, not the branch name [6].

### What Happens in Detached State

You **can** still make commits and modifications — Git treats this as an "anonymous branch." However, if you switch to another branch, these commits become orphaned and will eventually be deleted by Git's garbage collector (after about 30 days) unless you explicitly save them [6].

### How to Bypass or Fix Detached HEAD

**If you want to discard any work done in the detached state:**
```bash
# Simply switch back to a branch
git switch main        # preferred (Git 2.23+)
git checkout main      # older alternative
```

**If you want to SAVE work done in the detached state:**
```bash
# Create a new branch from your current (detached) position
git switch -c my-new-branch    # preferred
git checkout -b my-new-branch  # older alternative
```

**If you want to check out a remote branch properly without detaching:**
```bash
# Don't use: git checkout origin/feature  ← causes detached HEAD
# Use instead:
git switch feature    # Git auto-creates a local branch tracking the remote
```

**Prevention:** Use `git switch` (introduced in Git 2.23, August 2019) instead of `git checkout` for navigating branches. `git switch` will **refuse** to detach your HEAD and throws a fatal error (`a branch is expected`) if you try to switch to a raw commit or remote ref [6].

**Note:** During `git rebase`, Git briefly enters a detached HEAD state internally (via `git checkout --detach`) as part of its normal operation. This is harmless — it exits the detached state automatically when the rebase completes [2].
