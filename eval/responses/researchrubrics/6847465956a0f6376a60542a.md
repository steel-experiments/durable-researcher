# Technical Report: Scaling a Twitter-like Social Media Application to 1M Daily Active Users

## Executive Summary

Transitioning from a simple web interface backed by a single local MySQL database to a globally distributed platform serving 1 million daily active users requires a fundamental architectural overhaul. The local MySQL instance will become a catastrophic bottleneck under concurrent global read/write load. The recommended path forward is an incremental migration using the **Strangler Fig Pattern**, decomposing the monolith into containerized microservices orchestrated by Kubernetes, implementing a **Hybrid Fan-Out architecture** for timeline generation, introducing Redis caching and a CDN for global latency reduction, and sharding databases by `user_id`. This report provides a phased roadmap and concrete recommendations for every layer of the stack.

---

## 1. The Core Problem: Why the Current Architecture Fails

A single MySQL database on one server cannot handle the read/write throughput of 1M DAU. A Twitter-like app is overwhelmingly read-heavy (users scroll feeds far more than they post), and timeline generation is the single most expensive operation — it requires aggregating posts from every account a user follows, sorted by recency. At 1M users, even a simple `SELECT` joining follow relationships with posts will produce queries that take seconds, not milliseconds. The database becomes both a throughput bottleneck and a single point of failure [1][2][3].

## 2. Microservices Decomposition

### Recommended Service Boundaries

The monolith must be decomposed into domain-specific services, each owning its own data store [1][2][3]:

| Service | Responsibility | Data Owned |
|---|---|---|
| **User Service** | Registration, authentication, profiles | User accounts, credentials |
| **Post Service** | Message creation, retrieval, deletion | Posts, media references |
| **Social Graph Service** | Follow/unfollow relationships | Follower/following edges |
| **Feed/Timeline Service** | Home timeline generation & caching | Pre-computed feed caches |
| **Notification Service** | Push notifications, activity alerts | Notification state |
| **Media Service** | Image/video upload and processing | Object storage references |
| **API Gateway** | Routing, rate limiting, auth validation | None (stateless proxy) |

### Inter-Service Communication

- **Synchronous (REST or gRPC):** For real-time queries like fetching a user profile or validating auth tokens. gRPC is preferred for internal service-to-service calls due to lower latency and smaller payloads [3].
- **Asynchronous (Apache Kafka or RabbitMQ):** For event-driven workflows — when a post is created, the Post Service publishes an event; the Feed Service and Notification Service consume it independently. This decouples services and prevents cascading failures [2][3].

### Containerization & Orchestration

Package every service in Docker containers and orchestrate with **Kubernetes**. K8s provides horizontal pod auto-scaling (HPA) — automatically spinning up more Post Service replicas during traffic spikes — rolling deployments for zero-downtime updates, and self-healing via health checks [2][3]. Use an **NGINX Ingress Controller** for external routing [2].

## 3. Database Scaling Strategy

This is the most critical transition. A single MySQL instance must evolve into a distributed data layer.

### Phase 1: Read Replicas (Immediate)

Implement **master-slave replication** before any other change. All writes go to the master; all reads are distributed across read replicas. For a social app with a typical 100:1 read-to-write ratio, this alone can provide significant headroom [1][3].

### Phase 2: Database-per-Service

Assign each microservice its own database. The Post Service, User Service, and Social Graph Service should never share a database instance. This eliminates cross-service schema dependencies and allows each service to scale its data tier independently [2][3].

### Phase 3: Horizontal Sharding

Shard the Post and User databases across multiple nodes using **`user_id` as the shard key**. This is critical: sharding by `post_id` causes the "scatter-gather" problem, where building a single user's feed requires querying every shard. Sharding by `user_id` keeps a user's posts and profile localized to one node, making feed generation tractable [4][5].

**Mitigating hot partitions:** Celebrity accounts create disproportionate load on single shards. Use **consistent hashing** for even distribution and deploy dedicated read replicas for high-traffic shards [4][5].

### Phase 4: Specialized Data Stores

| Data Type | Recommended Store | Rationale |
|---|---|---|
| User accounts, auth | MySQL (sharded) or PostgreSQL | ACID compliance for critical data |
| Posts (high write volume) | Cassandra or DynamoDB | Distributed, write-optimized |
| Social graph (follows) | Neo4j or RedisGraph | Optimized for graph traversals |
| Session tokens | Redis | Sub-millisecond lookups |
| Media files | AWS S3 / GCS | Object storage with CDN integration |

Tools like **Vitess** (used by YouTube) can provide transparent MySQL sharding without changing application queries [4].

## 4. Timeline/Feed Architecture: The Hybrid Fan-Out Model

This is the defining architectural decision for a Twitter-like app. Two fundamental models exist [4][5][6]:

### Fan-Out on Write (Push Model)
When a user posts, the system immediately pushes that post into the timeline caches of **all followers**.
- ✅ Reads are O(1) — the timeline is pre-computed in Redis
- ❌ Severe write amplification — a user with 10,000 followers triggers 10,000 cache writes per post

### Fan-Out on Read (Pull Model)
When a user opens the app, the system queries the databases of everyone they follow, aggregates, and sorts in real time.
- ✅ Writes are fast — a post is stored only once
- ❌ Reads are expensive and slow — requires querying N databases for N followed accounts

### The Celebrity Problem
A user with 50M followers posting a single message in a pure Push model triggers 50 million synchronous cache writes, overwhelming workers and saturating the database. Conversely, a user following thousands of celebrities in a pure Pull model experiences severe latency while the system aggregates from numerous massive data sources [4][5][6].

### Recommended: Hybrid Approach

| User Type | Strategy | Rationale |
|---|---|---|
| Regular users (<100K followers) | **Fan-Out on Write** | Fast timeline reads for 99% of users |
| Celebrity users (>100K followers) | **Fan-Out on Read** | Prevents write amplification disasters |

**Implementation details:**
- All fan-out operations are asynchronous via **Kafka**. When a user posts, the Post Service writes to its database and publishes an event. Feed Service workers consume the event and update followers' Redis caches in the background [4][6].
- For celebrities, the post is stored once. When a regular user loads their feed, the system merges pre-computed timeline entries (from Push) with dynamically fetched celebrity posts (Pull) [5][6].
- Store only **lists of `post_id`s** in feed caches (not full post content) to minimize Redis memory footprint. Maintain separate Post Cache and User Cache for metadata "hydration" [4][5].
- **Accept eventual consistency.** Users tolerate a 2-second delay in celebrity content appearing, but will abandon the app if the timeline fails to load [5].

## 5. Caching & CDN Strategy

### Application-Level Caching (Redis)

- **Feed Cache:** Per-user timeline of `post_id` lists with TTL policies
- **Post Cache:** Full post content for rapid hydration
- **User Profile Cache:** Frequently accessed profile data
- **Session Store:** JWT tokens and session state
- **Social Graph Cache:** Follower counts, follow status lookups

All caches should use TTL expiration and cache-aside patterns (application checks cache first, falls back to database, then populates cache) [1][3][4].

### Content Delivery Network

Deploy a CDN (Cloudflare, AWS CloudFront) to serve:
- Static frontend assets (HTML, CSS, JS bundles)
- User-uploaded media (images, videos) via S3 + CDN
- **Public API responses** (e.g., trending posts, public profiles) can be cached at CDN edge locations to dramatically reduce origin server load [3][4].

### Anti-Cache-Stampede Measures

Implement request coalescing or cache-locking to prevent thousands of simultaneous cache misses from hitting the database at once during cache expiration events [6].

## 6. Migration Strategy: The Strangler Fig Pattern

Do **not** attempt a "big bang" rewrite. Martin Fowler's Strangler Fig Pattern is the industry-standard approach for this exact scenario [7]:

### Step-by-Step Migration

1. **Deploy an API Gateway** in front of the existing monolith. Initially, it routes all traffic to the legacy application transparently.

2. **Identify seams** — boundaries in the codebase where functionality can be isolated. Start with the **highest-read, lowest-risk** components: user profile reads and static content serving.

3. **Extract the first microservice** (e.g., User Profile Service). Build it with its own database. Route profile-related API calls from the Gateway to the new service; all other calls continue to the monolith.

4. **Migrate the Social Graph Service** next. Move follower/following data to its own data store (consider Neo4j for graph traversal performance).

5. **Build the Feed Service** with the Hybrid Fan-Out architecture described above. Introduce Redis for timeline caching and Kafka for asynchronous fan-out processing.

6. **Migrate the Post Service** — the core write path. This is the highest-risk migration; do it last when team confidence and operational maturity are established.

7. **Decommission the monolith** once all traffic has been redirected. The legacy MySQL database can be retired once all data has been migrated to the new distributed stores.

Throughout this process, the application remains live. Users experience no downtime. Each extracted service can be independently scaled, monitored, and optimized [7].

## 7. Observability, Security & Operations

### Monitoring Stack
- **Metrics:** Prometheus + Grafana for real-time dashboards (request rates, error rates, p50/p95/p99 latencies, cache hit ratios)
- **Logging:** ELK Stack (Elasticsearch, Logstash, Kibana) for centralized log aggregation across all microservices
- **Error Tracking:** Sentry for real-time exception alerts
- **Tracing:** Jaeger or AWS X-Ray for distributed request tracing across service boundaries [1][2][3]

### Security
- Transition to **OAuth 2.0 + JWT** for authentication and authorization
- Implement **rate limiting** at the API Gateway to prevent abuse and DDoS
- Encrypt data **in transit** (TLS/HTTPS everywhere) and **at rest** (database encryption)
- Use **Kubernetes Secrets** or a vault service (HashiCorp Vault) for credential management [1][3]

### CI/CD
- Establish automated pipelines (GitHub Actions, Jenkins) for building Docker images, running tests, and deploying to Kubernetes
- Implement canary deployments to gradually roll out changes to a subset of users before full rollout [2]

### Capacity Planning
- Base infrastructure sizing on **Peak QPS**, not average QPS
- Provision **2x headroom** above peak to handle traffic spikes and failover events
- Calculate storage projections for 1-day, 1-month, and 1-year retention cycles [6]
- Implement **dead-letter queues** in Kafka for failed message processing and retry logic [6]
