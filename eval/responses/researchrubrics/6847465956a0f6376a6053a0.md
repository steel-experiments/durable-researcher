# Technical Proposal: Distributed Audio Streaming Platform with Live Chat

## 1. Executive Summary

This proposal outlines the architecture for a distributed audio streaming platform with an integrated live chat feature, designed for delivery across both browser and mobile environments. The system prioritizes low-latency audio delivery, horizontal scalability, and operational efficiency suited to a medium-sized engineering team without a dedicated platform operations division. The architecture employs a microservices backend orchestrated on Kubernetes, a Flutter-based cross-platform frontend, a hybrid streaming protocol strategy (WebRTC + HLS), and Redis Streams/NATS for messaging infrastructure.

---

## 2. System Architecture Overview

The system is decomposed into four principal layers:

| Layer | Responsibility | Key Technologies |
|-------|---------------|------------------|
| **Client** | Audio playback, UI, live chat interface | Flutter 3.24, WebAudio API, ExoPlayer/AVAudioEngine |
| **Edge / CDN** | Static asset caching, audio segment delivery, TLS termination | Cloud CDN (Azure CDN / CloudFront), Ingress Controllers |
| **Application Services** | Audio ingestion, stream management, chat relay, auth | Go microservices, Kubernetes, Istio service mesh |
| **Data & Messaging** | State persistence, event streaming, pub/sub, caching | PostgreSQL, Redis Streams, NATS, Cassandra |

## 3. Frontend Architecture

### 3.1 Cross-Platform Framework: Flutter 3.24 (Dart)

**Recommendation:** Flutter over React Native.

**Justification:**

- **Rendering Engine:** Flutter's Impeller engine (default since v3.20) delivers up to 30% improvement in frame rendering on high-end devices compared to the legacy Skia backend [1]. Its self-contained rendering pipeline bypasses native UI component dependencies, ensuring pixel-perfect consistency across iOS, Android, and Web — critical for a media application where UI timing affects perceived audio sync.
- **Compilation Model:** Flutter's Ahead-of-Time (AOT) compilation compiles Dart directly to native ARM machine code, eliminating the JavaScript bridge overhead inherent in React Native's JIT model [1][2]. For a continuous audio streaming application, this means mobile CPU cycles are preserved for media decoding rather than JavaScript execution.
- **Code Reuse:** Approximately 75% code sharing across native and web targets, reducing maintenance burden for a medium-sized team [1].
- **Ecosystem Maturity:** As of 2025, Flutter provides stable full web and desktop support with strong DevTools for performance profiling — essential for debugging audio buffer timing and rendering jank [2].

**Trade-off Acknowledged:** React Native offers a larger JavaScript ecosystem and may be preferable if the existing team has deep JS/TS expertise. However, for a media-intensive application where rendering performance directly impacts user experience, Flutter's architectural advantages are decisive [2].

### 3.2 Audio Pipeline (Dual Architecture)

The client implements a dual audio pipeline to leverage platform-specific optimizations while maintaining a unified Dart codebase:

**Browser Pipeline — WebAudio API:**
- Flutter compiles to WebAssembly (WASM) and provides seamless interop with HTML5/JS APIs [1][2].
- Custom JavaScript bindings to the WebAudio API are invoked from Dart, enabling low-latency audio routing, equalization, spatial audio, dynamic compression, and precise synchronization of distributed streams [1][2].
- The WebAudio API's `AudioContext` and `AudioWorklet` nodes allow granular control over buffer management and sample-accurate scheduling.

**Mobile Pipeline — Native Audio Engines:**
- **Android:** Integration with ExoPlayer via Dart FFI (Foreign Function Interface) for adaptive bitrate streaming, background playback, and audio focus management [1].
- **iOS:** Integration with AVAudioEngine for equivalent native DSP capabilities [1].
- This mirrors the WebAudio API's control granularity at the native level, ensuring feature parity across platforms.

### 3.3 Live Chat UI Component

The chat interface is implemented as a shared Flutter widget library, rendering message lists, input fields, and presence indicators. It connects to the backend via a persistent WebSocket connection, consuming a GraphQL subscription layer that enables efficient subscription to chat events without over-fetching user metadata [1].

## 4. Backend Architecture

### 4.1 Microservices on Kubernetes

The backend is decomposed into independently deployable services, each packaged as a container and orchestrated by Kubernetes:

| Service | Responsibility |
|---------|---------------|
| `audio-ingestion-service` | Receives and transcodes uploaded audio, segments into HLS chunks |
| `stream-management-service` | Manages active sessions, playback state, track metadata |
| `chat-relay-service` | Handles WebSocket connections, distributes messages to chat rooms |
| `auth-service` | JWT issuance/validation, user identity management |
| `user-service` | User profiles, preferences, listening history |
| `presence-service` | Tracks online status, listener counts per stream |

**Kubernetes Configuration:**
- **Service Discovery:** CoreDNS for internal service-to-service resolution [3].
- **Autoscaling:** Horizontal Pod Autoscaler (HPA) with custom metrics (e.g., active WebSocket connections per pod for the chat service, concurrent stream bandwidth for the audio service) [3].
- **Resource Isolation:** Strict CPU and memory limits on all pods (e.g., requests `256Mi` / limits `512Mi` memory) to prevent resource contention during peak load [3].
- **Configuration:** Environment-specific variables externalized via `ConfigMaps`; secrets managed via base64-encoded Kubernetes `Secrets` [3].
- **Networking:** `ClusterIP` services for internal-only traffic (databases, payment gateways); `LoadBalancer` / Ingress for externally exposed audio and chat endpoints routed through the CDN [3].

### 4.2 Service Mesh: Istio

Istio is deployed to secure inter-service communication with mutual TLS and enable advanced traffic management patterns including canary deployments — gradually routing a percentage of traffic to new service versions before full rollout [3].

### 4.3 Backend Language: Go

Go is selected for the microservices for the following reasons:
- Native concurrency model (goroutines) ideal for handling thousands of simultaneous WebSocket connections and streaming sessions [4].
- Low memory footprint and fast startup times — well-suited for Kubernetes pod lifecycle.
- Strong standard library for HTTP/2 and gRPC, facilitating efficient internal service communication.

## 5. Streaming Protocol Strategy

A hybrid protocol approach optimizes for different streaming scenarios:

| Scenario | Protocol | Latency | Justification |
|----------|----------|---------|---------------|
| **Live / Real-time audio** | WebRTC | ~500ms | Ultra-low latency via peer-to-peer or SFU architecture; natively supported in browsers and mobile SDKs [4] |
| **On-demand / VOD audio** | HLS (HTTP Live Streaming) | 10–30s (standard), sub-3s (LL-HLS) | Scales massively via CDN caching of segmented chunks; fault-tolerant delivery over variable mobile networks [4] |
| **Internal service-to-service** | gRPC (HTTP/2) | Sub-ms | Multiplexed, bidirectional binary streaming; Protocol Buffer serialization minimizes payload size [5] |

**Adaptive Bitrate Management:**
The system implements dynamic threshold buffers and adaptive bitrate allocation to maintain continuous playback during network instability — adjusting quality in real-time based on available bandwidth and buffer health [6].

## 6. Live Chat Architecture

### 6.1 Connection Layer: WebSockets

WebSockets provide persistent, full-duplex communication channels essential for low-latency text messaging synchronized with live audio streams [5]. The `chat-relay-service` (Go) manages WebSocket connections and scales horizontally behind a Kubernetes load balancer with sticky sessions or a Redis-backed session store.

### 6.2 Message Distribution: Redis Streams

Redis Streams is recommended over Kafka for chat message distribution:

- **Zero additional infrastructure:** Redis is already deployed for caching and session state, meaning Redis Streams leverages existing infrastructure [7].
- **Native consumer groups:** Supports acknowledgements, pending entries, and dead-letter-queue (DLQ) patterns out of the box [7].
- **At-least-once delivery:** Chat messages require at-least-once semantics, which Redis Streams support natively. Consumer-side idempotency (via message UUIDs) must be implemented to handle deduplication [7].
- **Persistence:** Must be configured with `appendonly yes` (AOF persistence) rather than default RDB snapshots to prevent chat log loss [7].

**Why not Kafka:** For workloads under ~1 million messages per day (expected at medium scale), Kafka's durable log architecture is disproportionate. Kafka requires partition planning, consumer rebalance tuning, and effectively demands a dedicated platform team — an overhead unjustified for a medium-sized company [7].

### 6.3 Real-time Command Dispatch: NATS

For audio control commands (play, pause, skip, seek) and lightweight inter-service signaling:

- NATS delivers **sub-millisecond latency** at the 99.7th percentile for small payloads [7].
- Single binary deployment with no external dependencies, offering Kubernetes-native deployment with built-in Prometheus metrics [7].
- Its "fire-and-forget" pub/sub model is ideal for ephemeral commands that don't require durable storage.

### 6.4 Consistency Model

A hybrid consistency approach is applied:

- **Audio streaming state** (track progress, listener counts): Eventual Consistency — high throughput is prioritized, and slight delays in state propagation are acceptable [5].
- **Live chat messages**: Causal Consistency to ensure messages are observed in correct order, combined with Read-Your-Writes Consistency so users immediately see their own sent messages [5].

## 7. Data Layer

### 7.1 Primary Database: PostgreSQL

Structured data (user accounts, stream metadata, chat history archives, billing) is stored in PostgreSQL with:

- **Streaming replication** for read scalability and failover.
- **Logical replication** for feeding change events into the event sourcing pipeline.
- **Row-level security** for multi-tenant data isolation if applicable.

### 7.2 Distributed Storage for Scale

| Technology | Use Case | Consistency |
|-----------|----------|-------------|
| **Apache Cassandra** | Write-heavy telemetry (listening events, analytics) | Eventual |
| **Redis** | Session state, presence tracking, rate limiting, caching | Strong (single-node) |
| **Azure Blob Storage / S3** | Audio file storage (origin for CDN) | Strong |
| **CockroachDB** (optional) | If strong consistency is required for multi-region deployments | Strong (distributed) [5] |

### 7.3 Event Sourcing with CQRS

State changes are persisted as ordered event streams, enabling distributed nodes to reconstruct local state consistently. The CQRS pattern separates the write model (command processing) from the read model (optimized query views), allowing each to scale independently [5].

### 7.4 Conflict-Free Replicated Data Types (CRDTs)

CRDTs are employed for managing shared state counters (e.g., concurrent listener counts, presence indicators) across distributed nodes without conflict bottlenecks, enabling multi-leader replication across regions [5].

## 8. CDN and Edge Delivery

### 8.1 CDN Configuration

Audio segments (HLS chunks) and static assets (HTML, CSS, JS bundles, images) are served through a CDN (Azure CDN, CloudFront, or equivalent):

- **Partial cache sharing** allows the CDN to serve partially cached content to new requests — when the first request triggers an origin fetch, subsequent requests can begin receiving data before the full asset is cached [8].
- **Cache invalidation** is managed via HTTP `Cache-Control` headers and distinct blob paths (not query strings, which break caching) [8].
- **Compression** (gzip/Brotli) is enabled at the CDN edge to reduce bandwidth for mobile networks [8].

### 8.2 Security at the Edge

- HTTPS/SSL enforced across all CDN endpoints to prevent mixed-content warnings in browsers [8].
- Token-based authentication secures audio streams against unauthorized access.
- CORS is configured on the CDN or storage endpoint to support cross-origin requests from browser and mobile web clients [8].
- Client-side fallback logic detects CDN unavailability and routes requests back to origin servers [8].

## 9. Observability and Monitoring

### 9.1 Metrics: Prometheus + Grafana

- **Prometheus** collects time-series metrics from Kubernetes pods, including audio buffer latency, active WebSocket connections, cache hit/miss ratios, and origin fetch durations [3][8].
- **Grafana** provides visualization dashboards for real-time operational awareness [3].
- NATS exposes built-in Prometheus metrics for command dispatch monitoring [7].

### 9.2 Logging: EFK Stack

The Elasticsearch, Fluentd, Kibana (EFK) stack is deployed as a sidecar pattern within audio and chat pods:

- Structured JSON logs contain **correlation IDs** (`requestId`, `userId`, `streamId`) for tracing requests across microservices [3].
- Fluentd aggregates logs from all pods; Kibana enables real-time search and visualization.

### 9.3 Tracing: OpenTelemetry

Distributed tracing via OpenTelemetry provides end-to-end visibility into request paths spanning the Flutter client → CDN → Ingress → microservices → database, enabling latency bottleneck identification.

## 10. Deployment Strategy

| Strategy | Application | Detail |
|----------|-------------|--------|
| **Canary Deployments** | Chat & streaming services | Gradually route 5% → 25% → 100% of traffic to new versions via Istio traffic management [3] |
| **Blue-Green Deployments** | Database migrations | Maintain two identical production environments; switch traffic atomically after validation [3] |
| **CI/CD Pipeline** | All services | Static audio assets deployed independently from Kubernetes application deployments using separate storage containers [8] |
| **Chaos Testing** | Full system | Simulate node failures and network partitions to validate failover behavior and consistency guarantees [5] |

## 11. Audio Codecs

For encoding and transmission, the following codecs are supported based on delivery context:

| Codec | Bitrate | Latency | Use Case |
|-------|---------|---------|----------|
| **AAC** | 64–256 kbps | ~5ms (Fraunhofer low-latency mode) | Default streaming codec; universal browser/mobile support; adaptive to varying network conditions [6] |
| **Opus** | 6–510 kbps | ~5–66ms | Voice-grade chat audio and live streaming; superior quality at low bitrates; mandatory in WebRTC |
| **LDAC** (Sony) | Up to 990 kbps | Variable | Premium high-fidelity tier (24-bit/96kHz); adaptive bitrate balancing quality against battery life [6] |

## 12. Scalability and Capacity Planning

| Component | Scaling Mechanism | Target |
|-----------|------------------|--------|
| Chat relay pods | HPA on WebSocket connection count | ~10K concurrent connections/pod |
| Audio streaming pods | HPA on bandwidth utilization | Auto-scale on egress bandwidth |
| Redis | Cluster mode with sharding | Partitioned by chat room hash |
| NATS | Cluster deployment (3+ nodes) | Fault-tolerant, minimal tuning |
| CDN | Provider-managed elastic scaling | Automatic geographic distribution |
| PostgreSQL | Read replicas + connection pooling (PgBouncer) | Scale reads; writes on primary |

## 13. Risk Assessment and Mitigations

| Risk | Impact | Mitigation |
|------|--------|-----------|
| WebSocket connection storms during popular live events | Chat service overload | Rate limiting at Ingress; connection queuing; auto-scaling with predictive triggers |
| Audio sync drift across distributed clients | Poor user experience | Adaptive buffer management; NTP-synchronized timestamps; client-side drift correction via WebAudio API scheduling |
| Redis single-point-of-failure | Chat message loss | Redis Sentinel or Cluster for HA; AOF persistence; cross-region replication |
| CDN cache stampede on new content releases | Origin server overload | Request coalescing at CDN edge; staggered rollout of new content |
| Mobile battery drain from continuous streaming | User churn | Hardware-accelerated decoding (DSP offload); adaptive bitrate reducing CPU load [6] |
