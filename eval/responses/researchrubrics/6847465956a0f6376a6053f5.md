# Cross-Platform Anti-Cheat System Design for Competitive FPS
## Scalable to 1 Million Concurrent Users

---

## 1. Executive Summary

This document presents a server-authoritative, cross-platform anti-cheat system for a competitive first-person shooter, designed to scale to 1 million concurrent players. The architecture prioritizes **server-side detection** to minimize client overhead (<1.5% CPU, <1 ms input latency) and ensure true cross-platform compatibility (Windows, Linux, macOS, consoles). The multi-layered detection pipeline combines deterministic heuristics, behavioral analysis, and GPU-accelerated deep learning inference to achieve a projected >98% true positive rate and <2% false negative rate. Estimated cloud infrastructure costs at peak load (1M concurrent users) are approximately **$62,000–$75,000 per day** on AWS (US-East, July 2025 pricing).

## 3. Outline of Plan

### Phase 1: Foundation (Months 1–3)
- **Client SDK Development:** Build a lightweight telemetry SDK in C/C++ (compiled to <2 MB) that captures input events, view angles, memory integrity hashes, and hardware fingerprints. Platform-specific: kernel driver for Windows, user-space daemon for Linux/macOS/console.
- **Server-Side Authority:** Ensure all physics, hit-registration, and movement validation happens server-side. The game server is the single source of truth for state.
- **Telemetry Schema Design:** Define protobuf-based telemetry messages (~200 bytes per event, batched 10×/sec = ~2 KB/sec per player; with encryption overhead, ~5 KB/sec).

### Phase 2: Detection Pipeline (Months 3–6)
- **Heuristic Engine:** Implement deterministic rules (velocity > max, aim snap > human threshold, hit rate exceeding statistical bounds for rank).
- **ML Model Training:** Collect labeled datasets (see Test Methodology) and train temporal models: 1D-CNNs for aim pattern analysis, LSTMs for behavioral sequence detection.
- **Ensemble Verdict Logic:** Combine heuristic flags and ML confidence scores via a weighted state machine.

### Phase 3: Infrastructure & Scale (Months 6–9)
- Deploy auto-scaling ingestion (MSK Kafka) and processing (Flink + GPU fleet) on AWS.
- Implement delayed ban system (24–72 hour random delay) to prevent reverse-engineering of detection methods [1].
- Build moderator dashboard for human review of edge cases.
- Implement hardware-ID bans to reduce repeat offenders [1].

### Phase 4: Testing & Iteration (Months 9–12)
- Execute reproducible test methodology (see Section 7).
- Tune detection thresholds for >98% TPR and <2% FNR.
- Conduct adversarial red-team testing with private cheat development.

## 4. Detection Pipeline Description

### Stage 1: Client-Side Telemetry Capture
The lightweight SDK (<2 MB, <1.5% CPU, <5 MB RAM) runs alongside the game client. It captures:
- **Input events:** Mouse movements, keyboard presses (sampled at tick rate, ~64–128 Hz)
- **View angle sequences:** Per-frame camera rotation vectors for aimbot detection
- **Memory integrity hashes:** Periodic checksums of critical game memory regions
- **Hardware fingerprint:** GPU/Vendor ID, CPU model, peripheral device IDs
- **Platform metadata:** OS version, driver versions, anti-tamper status

On **Windows**, an optional kernel-level driver provides deeper memory protection. On **Linux, macOS, and consoles**, only user-space collection is used. The SDK uses AES-256-GCM encryption and certificate pinning to prevent packet tampering.

### Stage 2: Server-Side State Validation
The game server validates all critical state:
- Movement speed ≤ maximum velocity
- Line-of-sight verification for hit registration
- Physics consistency checks
This prevents basic tampering (speed hacks, teleportation) with zero client overhead.

### Stage 3: Heuristic Pre-Filter (Apache Flink)
Ingested telemetry streams pass through deterministic rules in a managed Apache Flink application:
- **Velocity anomalies:** Movement exceeding server-confirmed maximums
- **Aim snap detection:** Crosshair jumping to target in <1 frame
- **Inhuman reaction time:** Consistent reactions <150ms to newly visible targets
- **Statistical outliers:** Kill/death ratios, headshot percentages exceeding 99.9th percentile for rank
- **Memory integrity failures:** Checksum mismatches indicating code injection

This stage catches ~60–70% of cheats immediately with near-zero false positives (deterministic rules on server-authoritative data). Flink processes ~5 GB/sec across ~5,000 KPUs at $0.11/KPU-hour (~$550/hr) [2][3].

### Stage 4: ML Inference (GPU Fleet)
Telemetry that passes heuristics enters the ML pipeline on auto-scaling EC2 G5/G6 instances:
- **1D-CNN Model:** Analyzes aim pattern micro-movements across temporal windows (last 5–30 seconds). Detects aimbot smoothing, recoil control patterns, and robotic aim trajectories.
- **LSTM Model:** Processes behavioral sequences (movement patterns, target selection, engagement timing) to detect ESP/wallhacks (reaction to unexposed enemies) and strategic anomalies.
- **Autoencoder:** Unsupervised anomaly detection trained on legitimate gameplay distributions to catch novel, unknown cheats.

Each G5 instance (1× NVIDIA A10G GPU, 24 GB VRAM) processes batched inference for ~2,000 concurrent users [4]. At 1M users: ~500 instances at $1.006/hr = **~$503/hr**.

### Stage 5: Ensemble Verdict Engine
A deterministic state machine aggregates all signals:

| Signal Source | Weight | Ban Threshold |
|---|---|---|
| Heuristic match (deterministic) | 100% | Immediate flag |
| ML confidence (aimbot) | 40% | >0.85 → flag |
| ML confidence (ESP) | 30% | >0.90 → flag |
| Anomaly autoencoder score | 20% | >3σ → escalate |
| Memory integrity failure | 100% | Immediate flag |

Bans are issued in **randomized waves** (24–72 hour delay) to prevent cheat developers from correlating detection with specific cheat features [1]. Repeat offenders receive hardware-ID bans [1].

### Cheater Mitigation Techniques (Inspired by Ricochet)
Rather than immediate bans (which help cheat developers iterate), the system can deploy:
- **Cloaking:** Make legitimate players invisible to suspected cheaters
- **Damage shielding:** Reduce damage dealt by suspected cheaters
- **Matchmaking segregation:** Shadow-pool confirmed cheaters together

## 6. Cross-Platform Design Decisions

### Platform Capability Matrix

| Feature | Windows | Linux/macOS | Console (Xbox/PS) |
|---|---|---|---|
| Kernel-level driver | ✅ Optional | ❌ Not possible | ❌ Not possible |
| User-space SDK | ✅ | ✅ | ✅ (via platform SDK) |
| Telemetry collection | ✅ Full | ✅ Full | ✅ Full |
| Memory integrity scans | ✅ Deep | ✅ User-space only | ✅ Via platform API |
| HW fingerprinting | ✅ | ✅ | ✅ (console ID) |
| Server-side detection | ✅ Equal | ✅ Equal | ✅ Equal |

**Critical insight:** Server-side detection is the **great equalizer** — all platforms receive equivalent protection regardless of client-side capability. Kernel-level drivers enhance client-side integrity on Windows but are not architecturally required [1]. This design ensures Linux and console players are not second-class citizens.

## 7. Reproducible Test Methodology

### 7.1 Dataset Generation

**Legitimate Gameplay Corpus:**
- Record 10,000+ hours of human gameplay across skill tiers (bronze to pro) using open-source FPS environments (e.g., Unreal Engine 5 Lyra Starter Game)
- Instrument the game to log all telemetry fields at production fidelity
- Include diverse hardware (controller, keyboard/mouse, different frame rates)

**Cheat Corpus:**
- 1,000+ hours of gameplay using categorized cheat tools:
  - Aimbots (smooth, snap, FOV-based) × 10 variants
  - ESP/Wallhacks × 8 variants
  - Speed hacks, teleportation × 5 variants
  - Script macros (recoil, rapid-fire) × 10 variants
  - Private/custom cheats sourced via bug-bounty-style program
- Each recording labeled with cheat type, activation timestamps, and severity

### 7.2 Performance Testing

| Metric | Method | Target |
|---|---|---|
| **CPU Overhead** | Windows Performance Analyzer on i7-12700K + RTX 3060, measure delta with/without SDK | < 1.5% average CPU |
| **Memory Overhead** | Process memory delta | < 5 MB RAM |
| **Input Latency** | High-speed camera (1000 fps) measuring mouse-to-display latency | < 1 ms added |
| **Network Bandwidth** | Wireshark capture of telemetry stream | < 5 KB/sec (compressed: <1 KB/sec) |
| **Build Size** | Measure final binary size delta | < 2 MB added to build |

### 7.3 Detection Accuracy Testing

**Procedure:**
1. Load-test the pipeline using Locust or k6, simulating 100,000–1,000,000 virtual clients replaying telemetry from the dataset
2. Mix legitimate and cheat recordings at varying ratios (1%, 5%, 10% cheaters)
3. Run 10 independent trials with randomized seeding

**Metrics & Targets:**

| Metric | Formula | Target |
|---|---|---|
| True Positive Rate (TPR) | TP / (TP + FN) | > 98% |
| False Negative Rate (FNR) | FN / (TP + FN) | < 2% |
| False Positive Rate (FPR) | FP / (FP + TN) | < 0.5% |
| Precision | TP / (TP + FP) | > 99% |
| Time-to-Detect (median) | Time from cheat activation to flag | < 30 seconds |
| Pipeline Throughput | Events processed / second | > 5 GB/sec |

**Note:** The requirement specifies TPR >98% and FNR <2%. Mathematically, TPR = 1 − FNR, so these are consistent constraints: if FNR < 2%, then TPR > 98% by definition. The stricter challenge is maintaining low FPR (<0.5%) simultaneously.

### 7.4 Adversarial Testing (Red Team)

1. Commission an independent security team to develop novel cheats not in the training set
2. Run these against the production pipeline in a staged environment
3. Measure detection rate for zero-day cheats; target >80% (heuristics + anomaly detection)
4. Iteratively retrain models on false negatives; measure convergence to >98% TPR

### 7.5 Statistical Validation

Apply **Wilson score intervals** to all rate metrics at 95% confidence:
- For TPR >98% with 10,000 cheat samples: the lower bound of the Wilson interval must exceed 97.5%
- For FPR <0.5% with 100,000 legitimate samples: the upper bound must remain below 0.6%

## 9. Uncertainty & Gaps

- **Console-specific SDK constraints:** Exact telemetry APIs available on Xbox/PlayStation dev kits are NDA-restricted; the design assumes standard platform SDK capabilities but implementation details would require platform holder partnerships.
- **G6 instance pricing:** AWS does not publicly list G6 instance pricing in a readily scrapable format as of July 2025; G5 pricing ($1.006/hr for g5.xlarge) is used as the baseline. G6 instances with NVIDIA L4 GPUs may offer 15–20% better price-performance.
- **False positive rate for novel cheats:** The >80% zero-day detection target is an estimate; actual performance depends on the quality of the anomaly autoencoder and the sophistication of novel cheats.
- **Data transfer cost optimization:** The largest cost component (~$1.6M/month at peak) assumes AWS standard egress rates ($0.09/GB). Significant savings may be available through AWS PrivateLink, VPC endpoints, or negotiated enterprise pricing — these were not modeled.
- **Flink KPU-hour rate:** Confirmed at $0.11/KPU-hr via Ververica [3]; however, the exact throughput per KPU for the specific ML models proposed would require benchmarking against production workloads. AWS guidance is ~1 MB/sec/KPU for complex ML applications [2].
- **Client-side overhead figures:** The <1.5% CPU and <5 MB RAM targets are design goals based on industry benchmarks for telemetry-only client agents. Actual overhead must be validated through the performance testing methodology described in Section 7.2.
