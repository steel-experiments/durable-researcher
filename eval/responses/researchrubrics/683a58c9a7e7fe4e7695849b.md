# High-Performance Double-Precision GEMM: A Practical Guide for AVX2, FMA, and Multi-Core CPUs

## 1. Introduction

General Matrix-Matrix Multiplication (GEMM) is the foundational operation behind scientific computing, deep learning, and signal processing. Formally, GEMM computes:

$$C \leftarrow \alpha AB + \beta C$$

where $A$ is $m \times k$, $B$ is $k \times n$, and $C$ is $m \times n$. A naive triple-nested loop performs $2mnk$ floating-point operations but touches memory $O(n^3)$ times, creating a severe mismatch with modern hardware: CPUs can compute far faster than memory can supply data. This report explains how to close that gap and extract over 90% of a modern CPU's theoretical peak performance using three key ideas—**cache blocking**, **SIMD vectorization (AVX2 + FMA)**, and **multi-core parallelism**—with annotated C code throughout.

> **Sources:** This guide synthesizes the approaches documented by the BLIS framework [1][2], the "How to Optimize GEMM" wiki by van de Geijn and Huang [3], and the GEMM_AVX2 reference implementation [4].

## 2. The Problem: Why Naive GEMM Is Slow

The naive implementation:

```c
// Naive GEMM: C += A * B (column-major storage)
for (int j = 0; j < n; j++)
    for (int i = 0; i < m; i++)
        for (int p = 0; p < k; p++)
            C[i + j * ldc] += A[i + p * lda] * B[p + j * ldb];
```

Each iteration of the inner loop loads one element of $A$, one of $B$, and one of $C$ from memory, performs one multiply and one add, then writes $C$ back. For large matrices, $C$ has long since been evicted from cache by the time it's needed again, so nearly every access is a cache miss. The CPU spends most of its time *waiting for memory*, not computing.

**The fix:** Restructure the computation so that data loaded into fast, small caches is reused many times before being evicted. This is the central principle behind all high-performance GEMM implementations [1][3].

## 3. Optimization 1: Register-Level Blocking — The Microkernel

### 3.1 From Scalar to 4×4 Blocks

The first optimization rewrites the innermost computation to update a small $m_r \times n_r$ block of $C$ at a time. For AVX2 with double precision, the canonical choice is $m_r = 4, n_r = 4$ (a 4×4 microkernel). Instead of computing one element per iteration, we compute 16:

$$C_{i:i+3,\, j:j+3} \;\mathrel{+}= \sum_{p} \; A_{i:i+3,\,p} \times B_{p,\,j:j+3}$$

The 16 elements of the $C$ block are held entirely in CPU vector registers throughout the computation, eliminating all intermediate stores.

### 3.2 AVX2 and FMA Intrinsics

AVX2 provides 16 **256-bit YMM registers** (`ymm0`–`ymm15`), each holding exactly **4 double-precision floats**. FMA3 (Fused Multiply-Add) instructions perform $a \times b + c$ in a single operation, effectively doubling throughput compared to separate multiply and add. On Haswell and later Intel/AMD cores, two FMA units can sustain **16 FLOPs per cycle** (2 FMAs × 4 elements × 2 ops each).

Key intrinsics used:

| Intrinsic | Purpose |
|-----------|---------|
| `_mm256_set1_pd(x)` | Broadcast scalar `x` to all 4 lanes of a YMM register |
| `_mm256_loadu_pd(ptr)` | Load 4 contiguous doubles from memory (unaligned) |
| `_mm256_fmadd_pd(a, b, c)` | Compute `a * b + c` (single FMA instruction) |
| `_mm256_storeu_pd(ptr, v)` | Store 4 doubles from YMM register to memory |

### 3.3 Annotated Microkernel Code

```c
#include <immintrin.h>

/*
 * dgemm_microkernel_4x4
 * ----------------------
 * Computes C(4x4) += A(4 x kc) * B(kc x 4)
 *
 * - A is stored column-major with leading dimension 'lda'.
 * - B is packed contiguously (4 doubles per column, kc columns).
 * - C is stored column-major with leading dimension 'ldc'.
 *
 * The 4x4 block of C (16 doubles) lives entirely in YMM registers.
 */
void dgemm_microkernel_4x4(int kc, const double *A, int lda,
                           const double *B, double *C, int ldc)
{
    // Load current C(4x4) into 4 YMM registers (one per column).
    // Each __m256d holds 4 doubles = one column of the 4x4 C block.
    __m256d c0 = _mm256_loadu_pd(&C[0 * ldc]);  // column 0
    __m256d c1 = _mm256_loadu_pd(&C[1 * ldc]);  // column 1
    __m256d c2 = _mm256_loadu_pd(&C[2 * ldc]);  // column 2
    __m256d c3 = _mm256_loadu_pd(&C[3 * ldc]);  // column 3

    // Main loop over the k dimension
    for (int p = 0; p < kc; p++) {
        // Broadcast A[p] (one scalar) to all 4 lanes
        // A column p, rows 0-3
        __m256d a_reg = _mm256_loadu_pd(&A[p * lda]);
        // (Alternatively, if A is packed contiguously: _mm256_loadu_pd(&A[p * 4]))

        // Load 4 contiguous doubles from row p of packed B
        __m256d b_reg = _mm256_loadu_pd(&B[p * 4]);

        // FMA: c_col += a_col * b_scalar  (for each of the 4 columns)
        c0 = _mm256_fmadd_pd(a_reg, _mm256_set1_pd(B[p * 4 + 0]), c0);
        c1 = _mm256_fmadd_pd(a_reg, _mm256_set1_pd(B[p * 4 + 1]), c1);
        c2 = _mm256_fmadd_pd(a_reg, _mm256_set1_pd(B[p * 4 + 2]), c2);
        c3 = _mm256_fmadd_pd(a_reg, _mm256_set1_pd(B[p * 4 + 3]), c3);
    }

    // Store updated 4x4 block back to C
    _mm256_storeu_pd(&C[0 * ldc], c0);
    _mm256_storeu_pd(&C[1 * ldc], c1);
    _mm256_storeu_pd(&C[2 * ldc], c2);
    _mm256_storeu_pd(&C[3 * ldc], c3);
}
```

**Why this is fast:** Inside the loop, each iteration performs **16 FLOPs** (4 FMA instructions × 4 doubles each) with only **2 memory loads** (one for A, one for B). That's a **compute-to-load ratio of 8:1**, keeping the arithmetic pipeline fully saturated. The 4 C-register accumulators are never written to memory until the entire k-dimension is processed [1][3].

### 3.4 Loop Unrolling

The inner loop can be further unrolled by a factor of 4 (or more) to eliminate loop-counter overhead and improve instruction-level parallelism:

```c
// Unrolled by 4
for (int p = 0; p < (kc & ~3); p += 4) {
    __m256d a0 = _mm256_loadu_pd(&A[(p+0) * 4]);
    __m256d a1 = _mm256_loadu_pd(&A[(p+1) * 4]);
    __m256d a2 = _mm256_loadu_pd(&A[(p+2) * 4]);
    __m256d a3 = _mm256_loadu_pd(&A[(p+3) * 4]);

    __m256d b0 = _mm256_loadu_pd(&B[(p+0) * 4]);
    __m256d b1 = _mm256_loadu_pd(&B[(p+1) * 4]);
    __m256d b2 = _mm256_loadu_pd(&B[(p+2) * 4]);
    __m256d b3 = _mm256_loadu_pd(&B[(p+3) * 4]);

    c0 = _mm256_fmadd_pd(a0, _mm256_set1_pd(B[(p+0)*4+0]), c0);
    c0 = _mm256_fmadd_pd(a1, _mm256_set1_pd(B[(p+1)*4+0]), c0);
    // ... continue for c1, c2, c3 and remaining b elements
}
```

Unrolling removes branch-prediction pressure and gives the CPU's out-of-order execution engine more instructions to schedule, keeping both FMA units busy every cycle [3].

## 4. Optimization 2: Cache Blocking (Tiling)

### 4.1 The Intuition

A single 4×4 microkernel is extremely fast for tiny matrices, but performance collapses when matrices exceed the L2 cache. The solution is **blocking** (also called tiling): partition the large matrices into cache-sized blocks, and restructure the loop nest to compute one block at a time, maximizing reuse of data already in cache.

Think of it like this: instead of reading an entire cookbook every time you need an ingredient, you set out all the ingredients for one recipe on your counter (cache) and cook the whole dish before putting anything away.

### 4.2 Three-Level Blocking (The BLIS Approach)

BLIS-style GEMM uses three levels of blocking, each targeting a specific cache level [1][2]:

```
┌──────────────────────────────────────────────┐
│  Loop 1: JC — partition B by NC columns      │  (L3-sized)
│  ┌──────────────────────────────────────────┐│
│  │  Loop 2: IC — partition A by MC rows     ││  (L3-sized)
│  │  ┌──────────────────────────────────────┐││
│  │  │  Loop 3: PC — partition K by KC      │││  (L2-sized)
│  │  │  ┌──────────────────────────────────┐│││
│  │  │  │  Loop 4: JR — NR columns of C    ││││  (Register-sized)
│  │  │  │  ┌──────────────────────────────┐││││
│  │  │  │  │  Loop 5: IR — MR rows of C   │││││  (Microkernel)
│  │  │  │  │  → dgemm_microkernel_4x4()   │││││
│  │  │  │  └──────────────────────────────┘││││
│  │  │  └──────────────────────────────────┘│││
│  │  └──────────────────────────────────────┘││
│  └──────────────────────────────────────────┘│
└──────────────────────────────────────────────┘
```

### 4.3 Choosing Block Sizes

Block sizes are tuned to the target CPU's cache dimensions. For a modern x86 core with 32 KB L1, 256 KB L2, and shared L3:

| Parameter | Typical Value | Constraint |
|-----------|--------------|------------|
| $m_r$ | 4 | Number of YMM registers for C accumulator rows |
| $n_r$ | 4 (or 8) | AVX2 width (4 doubles per YMM) |
| $k_c$ | 256–512 | $m_r \times k_c \times 8$ bytes must fit in L2 |
| $m_c$ | 64–128 | $m_c \times k_c \times 8$ bytes should fit in L2/L3 fringe |
| $n_c$ | 4096–8192 | $k_c \times n_c \times 8$ bytes should fit in L3 |

**Example:** With $k_c = 256$, $m_r = 4$: the A micro-panel is $4 \times 256 \times 8 = 8$ KB — easily fitting in L1. With $m_c = 96$: the full A panel is $96 \times 256 \times 8 \approx 192$ KB — fitting in L2 [1][2].

### 4.4 Blocked GEMM Loop Structure

```c
/*
 * dgemm_blocked — High-level driver with 3-level cache blocking.
 *
 * Computes C( m x n ) += A( m x k ) * B( k x n )
 * Column-major storage throughout.
 */
#define MC  96
#define NC  4096
#define KC  256
#define MR  4
#define NR  4

void dgemm_blocked(int m, int n, int k, const double *A, int lda,
                   const double *B, int ldb, double *C, int ldc)
{
    // Allocate thread-local packing buffers
    double packed_A[MC * KC];  // ~192 KB
    double packed_B[KC * NC];  // ~8 MB

    for (int jc = 0; jc < n; jc += NC) {                  // Loop 1: L3 block of B
        int nb = min(NC, n - jc);
        for (int pc = 0; pc < k; pc += KC) {              // Loop 3: K-dimension block
            int pb = min(KC, k - pc);
            pack_B(&B[pc + jc * ldb], ldb, pb, nb, packed_B);  // Pack B panel

            for (int ic = 0; ic < m; ic += MC) {           // Loop 2: L3 block of A
                int mb = min(MC, m - ic);
                pack_A(&A[ic + pc * lda], lda, mb, pb, packed_A);  // Pack A panel

                // Invoke microkernel over all MR×NR tiles
                for (int jr = 0; jr < nb; jr += NR) {      // Loop 4
                    for (int ir = 0; ir < mb; ir += MR) {   // Loop 5
                        dgemm_microkernel_4x4(pb,
                            &packed_A[ir * pb], pb,
                            &packed_B[jr],
                            &C[(ic + ir) + (jc + jr) * ldc], ldc);
                    }
                }
            }
        }
    }
}
```

## 5. Optimization 3: Packing (Contiguous Memory Layout)

### 5.1 Why Packing Matters

Even with blocking, accessing a sub-matrix within a column-major array means **striding through memory** by the leading dimension. For a 10000×10000 matrix, accessing column 0, then column 1, means jumping 10000 × 8 = 80 KB between loads — wasting cache lines and causing TLB (Translation Lookaside Buffer) misses. Packing copies the needed sub-matrix into a **contiguous buffer**, so the microkernel marches through memory linearly [1][3].

### 5.2 Packing Functions

```c
/*
 * pack_A — Copy an mc × kc panel of A into contiguous memory.
 * Each MR-row group is stored contiguously (row-major within the panel).
 */
void pack_A(const double *A, int lda, int mc, int kc, double *packed)
{
    for (int i = 0; i < mc; i += MR) {
        for (int p = 0; p < kc; p++) {
            for (int ir = 0; ir < MR; ir++) {
                *packed++ = A[(i + ir) + p * lda];
            }
        }
    }
}

/*
 * pack_B — Copy a kc × nc panel of B into contiguous memory.
 * Stored column-major so each NR-column group is contiguous.
 */
void pack_B(const double *B, int ldb, int kc, int nc, double *packed)
{
    for (int j = 0; j < nc; j += NR) {
        for (int p = 0; p < kc; p++) {
            for (int jr = 0; jr < NR; jr++) {
                *packed++ = B[p + (j + jr) * ldb];
            }
        }
    }
}
```

**Cost amortization:** Packing B is done once per JC/PC iteration pair and reused across all IC iterations. Packing A is done once per IC/PC pair and reused across all JR/IR tiles. The cost of copying is $O(m_c \cdot k_c + k_c \cdot n_c)$ — negligible compared to the $O(m_c \cdot n_c \cdot k_c)$ FLOPs the microkernel performs on the packed data [1][3].

## 6. Optimization 4: Multi-Core Parallelization

### 6.1 Strategy: Parallelize the Outermost Loop

The key principle is to **parallelize at the coarsest granularity** (the JC or IC loop) so that each thread owns a distinct region of the output matrix $C$. This eliminates write-contention: no two threads ever write to the same element of $C$ [1][4].

```c
void dgemm_parallel(int m, int n, int k, const double *A, int lda,
                    const double *B, int ldb, double *C, int ldc,
                    int nthreads)
{
    // Allocate per-thread packing buffers to avoid false sharing
    double *packed_A_bufs = malloc(nthreads * MC * KC * sizeof(double));
    double *packed_B      = malloc(KC * NC * sizeof(double));  // shared read-only

    #pragma omp parallel num_threads(nthreads)
    {
        int tid = omp_get_thread_num();
        double *my_packed_A = &packed_A_bufs[tid * MC * KC];

        #pragma omp for schedule(dynamic)
        for (int jc = 0; jc < n; jc += NC) {
            int nb = min(NC, n - jc);
            for (int pc = 0; pc < k; pc += KC) {
                int pb = min(KC, k - pc);
                pack_B(&B[pc + jc * ldb], ldb, pb, nb, packed_B);

                for (int ic = 0; ic < m; ic += MC) {
                    int mb = min(MC, m - ic);
                    pack_A(&A[ic + pc * lda], lda, mb, pb, my_packed_A);

                    for (int jr = 0; jr < nb; jr += NR) {
                        for (int ir = 0; ir < mb; ir += MR) {
                            dgemm_microkernel_4x4(pb,
                                &my_packed_A[ir * pb], pb,
                                &packed_B[jr],
                                &C[(ic + ir) + (jc + jr) * ldc], ldc);
                        }
                    }
                }
            }
        }
    }

    free(packed_A_bufs);
    free(packed_B);
}
```

### 6.2 Key Design Decisions

- **`schedule(dynamic)`:** When matrix dimensions aren't perfectly divisible by block sizes, dynamic scheduling balances work across threads by assigning JC iterations on-demand.
- **Thread-local packing buffers:** Each thread has its own `packed_A` buffer (typically ~192 KB). This prevents **false sharing** — where two threads unknowingly contend for the same cache line.
- **Shared read-only B buffer:** The packed B panel is shared across threads (read-only), saving memory and packing overhead.
- **Near-linear scaling:** Because each thread performs $O(m_c \cdot n_c \cdot k_c)$ FLOPs between synchronization points, the parallelization overhead is negligible. The GEMM_AVX2 project demonstrates **>90% parallel efficiency** on multi-core Haswell/Skylake/Zen processors [4].

## 8. Conclusion

High-performance GEMM is not about writing clever arithmetic — it is about **managing the memory hierarchy**. The four pillars are:

1. **The microkernel** (AVX2 + FMA intrinsics) saturates the FMA units by keeping a 4×4 block of $C$ in registers.
2. **Cache blocking** restructures the loop nest so each cache level feeds the one below it, reducing memory traffic from $O(n^3)$ to $O(n^2)$.
3. **Packing** eliminates strided memory access within the microkernel, ensuring every loaded cache line is fully consumed.
4. **Multi-core parallelism** distributes independent $C$-blocks across threads with zero write contention.

Together, these techniques transform a naive implementation running at 1–5% of peak into one sustaining **over 90% of theoretical peak GFLOPs** — competitive with vendor-optimized libraries like Intel MKL [4].
