# Building a Simple Agentic AI for Personal Mental-Wellness Support

## Executive Summary

A two-agent architecture — a **Mood Agent** that analyzes check-ins and an **Intervention Agent** that delivers exercises — is well-suited to an orchestration framework like **LangGraph** (for deterministic, auditable routing) or **CrewAI** (for faster prototyping). Dialogflow CX or Rasa handle the NLU layer for text and voice emotion detection. All data must be AES-256 encrypted at rest, TLS 1.2+ in transit, and users must be given a hard-delete mechanism. A 2-week pilot with 20 users measuring engagement and self-reported mood improvement is a validated starting point, using instruments like PHQ-4 or a simple 1–10 mood scale.

---

## 1. Architecture Overview

### 1.1 The Two-Agent Design

| Agent | Role | Input | Output |
|---|---|---|---|
| **Mood Agent** | Reads user check-ins (text or voice), classifies emotional valence and intensity | Free-text or voice memo | Mood label + severity score (e.g., 1–10) |
| **Intervention Agent** | Suggests a targeted micro-exercise based on the flagged mood | Mood label + severity + context | Breathing exercise, journaling prompt, grounding technique, etc. |

**Workflow routing:** The Mood Agent processes every check-in. If it flags an extremely low or high mood, it pings the Intervention Agent, which immediately delivers an appropriate exercise. If the input is ambiguous, the Mood Agent asks a clarifying follow-up question rather than guessing. If a user logs low mood **3 consecutive times**, the system escalates to a human counselor.

### 1.2 Orchestration Framework Comparison

Three leading frameworks are relevant:

| Framework | Strengths | Best For | Fit for This Project |
|---|---|---|---|
| **LangGraph** | Stateful directed-graph execution, checkpoint/recovery, step-level visual traces, deterministic paths | Predictable state machines needing auditability and replayability | ★★★★★ — Ideal. The escalation logic (3× low → human) maps naturally to a graph with defined state transitions. Checkpointing ensures user state is never lost mid-conversation. |
| **CrewAI** | Hierarchical role-based "crews," shared memory (SQLite), fast setup, YAML configuration | Rapid prototyping, structured team-based automation | ★★★★ — Great for MVP. Quick to stand up the two-agent "crew" with role definitions. Less deterministic than LangGraph for the escalation path. |
| **AutoGen** | Conversational turn-taking, self-critique loops, enterprise maturity | Collaborative agent workflows requiring negotiation | ★★★ — Overkill for a simple 2-agent system. Better suited for multi-agent research or code-generation tasks. |

**Recommendation:** Start with **CrewAI** for a fast prototype, then migrate to **LangGraph** once you need deterministic escalation guarantees and audit trails. If you want to skip the prototype phase and go straight to something production-grade, LangGraph from the start is the safer bet.

## 2. NLU & Emotion Detection Layer

### 2.1 Dialogflow CX (Recommended for Your Use Case)

Dialogflow CX is Google's enterprise-grade conversational AI platform and fits this project for several reasons:

- **Voice + text input** — Dialogflow CX natively handles both telephony/voice integrations and text-based chat, which matches your requirement for voice check-ins.
- **Intent classification + sentiment analysis** — Built-in sentiment analysis scores each user utterance on a magnitude/valence scale, giving your Mood Agent an immediate emotional read.
- **Webhook integration** — You can wire Dialogflow fulfillment webhooks directly into your agent orchestration layer (LangGraph or CrewAI), passing mood scores downstream.
- **Clarification fallbacks** — Dialogflow CX supports "no-match" intents and follow-up question flows out of the box, handling the case where the bot is confused.

### 2.2 Rasa (Open-Source Alternative)

If you need full control over the NLU model or want to avoid Google Cloud vendor lock-in:

- **Rasa** is an open-source conversational AI framework that lets you train custom intent classifiers and entity extractors.
- You can plug in a **fine-tuned sentiment/emotion model** (e.g., a DistilBERT variant trained on emotion datasets like GoEmotions) into Rasa's NLU pipeline.
- Rasa runs entirely on your infrastructure, simplifying HIPAA compliance since data never leaves your environment.

### 2.3 LLM-Based Emotion Extraction

A third option: skip the traditional NLU platform and use an LLM (e.g., GPT-4o-mini or Claude Haiku) with a structured prompt to extract mood:

```
Given this user check-in: "{user_input}", extract:
1. Primary emotion (happy, sad, anxious, angry, neutral, mixed)
2. Intensity (1-10)
3. Key triggers mentioned (if any)
4. Confidence level of your assessment
If confidence < 0.7, suggest a follow-up question to clarify.
Return as JSON.
```

This approach is the most flexible and requires the least setup, but you **must use a private endpoint** (not the public API) to maintain data confidentiality, and you must have a BAA in place with the provider for HIPAA compliance.

## 3. Escalation & Safety Protocols

### 3.1 The 3-Strike Rule

Implement a rolling window state tracker:

```
User checks in → Mood Agent scores mood (1-10)
If mood ≤ 3:
    consecutive_low_count += 1
else:
    consecutive_low_count = 0

If consecutive_low_count >= 3:
    TRIGGER: Escalate to human counselor
    ACTION: Bypass generative responses entirely
    MESSAGE: "I've noticed you've been feeling low for a while. 
              I'd like to connect you with someone who can help."
```

This logic maps cleanly to a **LangGraph conditional edge** — a deterministic graph transition that is fully auditable.

### 3.2 Crisis Keyword Detection

In parallel with mood scoring, implement a **deterministic crisis keyword scanner** (regex or simple classifier) that watches for high-risk language (e.g., mentions of self-harm, suicide, or hopelessness). If triggered, the system should:

1. **Immediately bypass all generative responses** — no chatbot output.
2. **Display a deterministic, pre-written crisis message** with hotline numbers (988 Suicide & Crisis Lifeline, Crisis Text Line).
3. **Escalate to a human counselor** regardless of the consecutive-low counter.

This hybrid approach — LLM mood assessment + deterministic crisis guardrails — is the industry standard, used by platforms like Wysa and Woebot.

### 3.3 Disclaimers & Scope Boundaries

The bot must never:
- Diagnose mental health conditions
- Prescribe or recommend medication
- Present itself as a therapist or medical professional

Every session should begin with a clear disclaimer: *"I'm a wellness support tool, not a therapist. If you're in crisis, please call 988."*

## 4. Data Security, Encryption & User Data Deletion

### 4.1 Encryption Requirements

| Layer | Standard | Implementation |
|---|---|---|
| **Data at rest** | AES-256 | All check-in text, voice recordings, mood scores, and conversation logs encrypted using AES-256 with keys managed through a KMS or HSM |
| **Data in transit** | TLS 1.2+ | All API calls, webhook transmissions, and client-server communications |
| **Voice recordings** | Encrypted at capture | If storing voice memos, encrypt immediately upon ingestion; consider transcribing and then deleting the audio file to minimize stored PII |

### 4.2 HIPAA Compliance Checklist

If you're handling mental health data for US users, HIPAA applies:

- **Business Associate Agreements (BAAs)** required with every third-party vendor (cloud provider, LLM API provider, Dialogflow/Google Cloud).
- **Role-Based Access Control (RBAC)** — only authorized personnel can access user data.
- **Audit trails** — log every access to user data with timestamps and actor identity.
- **Data minimization** — only collect what you need; don't store raw audio if a transcript suffices.
- **Private LLM endpoints** — use Azure OpenAI Service or AWS Bedrock (which offer BAAs) rather than the public OpenAI API.

If you're targeting EU users, GDPR adds requirements for explicit consent, a Data Protection Impact Assessment (DPIA), and the right to erasure.

### 4.3 User Data Deletion

You must implement a **hard-delete function**:

```python
def delete_user_history(user_id: str):
    # 1. Delete from primary database
    db.checkins.delete_many({"user_id": user_id})
    db.mood_scores.delete_many({"user_id": user_id})
    
    # 2. Delete from encrypted backups (mark for purge on next backup cycle)
    backup_service.schedule_purge(user_id)
    
    # 3. Delete voice recordings from object storage
    storage.delete_folder(f"voice/{user_id}/")
    
    # 4. Delete from agent memory / vector store
    vectorstore.delete_by_metadata({"user_id": user_id})
    
    # 5. Log the deletion (audit trail) without retaining content
    audit_log.record(user_id, "DATA_DELETED", timestamp=now())
```

This must purge data from **all** storage layers — primary DB, backups, object storage, and vector stores (if using RAG).

## 5. Pilot Testing Plan

### 5.1 Study Design

| Parameter | Detail |
|---|---|
| **Participants** | 20 users (convenience sample; consider screening for mild-moderate stress/anxiety) |
| **Duration** | 2 weeks |
| **Check-in frequency** | Users asked to check in at least once daily (morning or evening) |
| **Design** | Single-arm pre/post feasibility study (no control group for an MVP) |

### 5.2 Outcome Measures

**Primary metrics:**

1. **Engagement rate** — Number of check-ins completed / number expected (14 days × 1/day = 14). Track daily active usage, completion rates, and drop-off points.
2. **Self-reported mood improvement** — Use a validated ultra-brief scale:
   - **PHQ-4** (4 items, ~1 min): screens for depression + anxiety. Administer at baseline and Day 14.
   - Or a **simple 1–10 mood rating** at every check-in, then compare average mood in Week 1 vs. Week 2.

**Secondary metrics:**

3. **Intervention uptake** — Did the user actually do the breathing exercise or journaling prompt suggested? (Self-reported via a quick button tap.)
4. **Escalation events** — How many users triggered the 3× low-mood escalation? How many triggered the crisis keyword scanner?
5. **User satisfaction** — A short post-pilot survey (5–7 questions) covering perceived helpfulness, ease of use, trust, and likelihood of continued use. Use a Likert scale (1–5).
6. **Follow-up question rate** — How often did the Mood Agent need to ask clarifying questions? (Helps refine the NLU model.)

### 5.3 Data Collection & Analysis

- **Quantitative:** Compare pre/post PHQ-4 scores using a paired t-test or Wilcoxon signed-rank test (n=20 is small, so non-parametric is safer). Plot engagement over time (day-by-day retention curve).
- **Qualitative:** Conduct 15-minute exit interviews (or open-text survey) asking users what they liked, what felt off, and whether they trusted the system with their emotional data.

### 5.4 Ethical Safeguards for the Pilot

- **Informed consent** — Users must understand this is a wellness tool, not therapy.
- **Right to withdraw** — Users can drop out at any time and delete all data.
- **IRB review** — If affiliated with a university or hospital, institutional review is required. For an independent project, consider a lightweight ethical review with a mental health professional.
- **Crisis protocol during pilot** — Ensure every escalation actually reaches a real human counselor (even if it's a single designated clinician or a crisis line warm handoff).

## 6. Recommended Tech Stack Summary

| Layer | Tool | Rationale |
|---|---|---|
| **Agent Orchestration** | LangGraph (production) or CrewAI (prototype) | Deterministic state graphs for escalation logic |
| **NLU / Voice** | Dialogflow CX | Native voice + text, built-in sentiment analysis, webhook support |
| **Emotion Classification** | LLM structured output (GPT-4o-mini / Claude Haiku via private endpoint) or fine-tuned DistilBERT | Flexible, handles nuance in free-text check-ins |

| **Voice Storage** | AWS S3 (encrypted bucket, auto-delete after transcription) | Temporary voice file handling |
| **Vector Store** | pgvector or Pinecone (with BAA) | If using RAG for intervention content |
| **LLM Provider** | Azure OpenAI Service or AWS Bedrock | HIPAA-compliant endpoints with BAAs |
| **Frontend** | React Native or Flutter (mobile) / React (web) | Cross-platform user interface |
| **Observability** | Langfuse or LangSmith | Step-level tracing of agent decisions |

## 7. Risks & Considerations

- **LLM loneliness correlation** — A joint study by OpenAI and the MIT Media Lab found that high chatbot usage can correlate with *increased* loneliness. Your system should be designed to augment (not replace) human connection, which your escalation-to-human-counselor feature addresses.
- **Cultural sensitivity** — Emotion expression varies across cultures. Ensure training data and prompt design are inclusive.
- **Regulatory gray zone** — Wellness apps that don't make clinical claims are generally not regulated as medical devices (FDA), but this boundary is evolving. Use careful disclaimers.
- **Small sample caution** — A 20-person, 2-week pilot proves feasibility and usability, not clinical efficacy. Don't over-claim results.
