# MLOps Platforms for Real-Time Fraud Detection: Comparative Analysis

## Executive Summary

Based on analysis of four leading open-source MLOps platforms—Seldon Core 2 with Triton Inference Server, Ray Serve, KServe, and BentoML—no single platform dominates across all dimensions critical for a 50M daily transaction fraud detection system across India, Indonesia, and Philippines. **KServe** offers the strongest Kubernetes-native story for ensemble pipelines with built-in A/B testing and drift detection. **Seldon Core 2 + Triton** provides the most production-hardened GPU-accelerated pipeline for gradient boosting models via NVIDIA's FIL backend. **Ray Serve** excels at complex model composition in pure Python but requires custom tooling for operational concerns. **BentoML** offers the fastest path to initial deployment but has thinner enterprise operational features. Specific published benchmarks from Razorpay, Gojek, and PayMongo on their fraud detection infrastructure were not discoverable in public sources.

## 1. Platform Architecture & Ensemble Model Support

### Seldon Core 2 + Triton Inference Server

Seldon Core 2 is a Kubernetes-native framework explicitly designed for deploying and managing ML systems at scale across cloud, on-premise, and hybrid environments [1]. Its modular, data-centric architecture allows it to serve as an orchestration layer that can wrap NVIDIA Triton Inference Server as the underlying inference engine. Triton's **FIL (Forest Inference Library) backend** is the critical component for ensemble fraud detection: it provides highly optimized, real-time deployment of tree-based models including **XGBoost** (JSON and binary formats), **LightGBM** (text files), scikit-learn, and RAPIDS cuML [5]. The FIL backend supports batching up to **32,768** and includes built-in dynamic batching configuration to group incoming requests—directly relevant for handling 10x burst traffic scenarios [5]. Critically, FIL automatically utilizes NVIDIA GPUs when available and falls back to CPU-only execution, making it ideal for mixed CPU/GPU infrastructure [5]. Triton also includes a dedicated **"categorical-fraud-detection"** Jupyter notebook example, lowering the engineering barrier for initial deployment [5].

**Neural network models** would be served via Triton's native TensorFlow, PyTorch, or ONNX Runtime backends alongside the FIL backend, with Seldon Core 2 orchestrating the ensemble routing. This is architecturally the cleanest separation: gradient boosting on FIL, neural networks on TensorRT/ONNX, both behind Seldon's unified API.

### Ray Serve

Ray Serve takes a fundamentally different approach—it is a **programmable model serving library** built on top of the Ray distributed computing framework [2]. Its defining strength is **model composition**: complex inference services combining multiple ML models and business logic can be expressed entirely in Python code [2]. For an ensemble combining XGBoost, LightGBM, and neural networks, Ray Serve allows developers to chain or fan-out inference calls within a single decorated Python class hierarchy. It supports fractional GPU sharing, enabling multiple models to share a single GPU for cost efficiency—a significant advantage when running multiple model frameworks simultaneously [2]. Ray scales to multi-node, multi-GPU deployments natively.

However, Ray Serve is **not Kubernetes-native** in the same way as Seldon or KServe. It runs as a Ray cluster (which can be deployed on Kubernetes), but operational tooling like canary rollouts, A/B traffic splitting, and drift detection must be built custom or integrated with external tools.

### KServe

KServe is the **open-source standard for self-hosted AI on Kubernetes**, built on Kubernetes CRDs (Custom Resource Definitions) via the `InferenceService` resource [3]. Its most relevant feature for fraud detection ensembles is the **InferenceGraph** capability, which enables creation of complex inference pipelines, ensembles, and multi-model workflows [3]. KServe provides native multi-framework runtime support: XGBoost, LightGBM (via MLServer), TensorFlow, PyTorch, scikit-learn, and ONNX models are all first-class citizens [3]. Each component of the ensemble can be deployed as a separate `InferenceService` and composed via the InferenceGraph, which supports sequence, ensemble, and switch routing patterns.

KServe's cold-start latency is mitigated through **intelligent model caching**, which decreases loading times for frequently used models [3]. It also provides KV cache offloading to CPU/disk for memory management.

### BentoML

BentoML positions itself as a **Unified Inference Platform** with both an open-source serving framework and a managed cloud service (BentoCloud) [4][6]. Version 1.2 introduced a distributed "Service-dependent graph" architecture where multiple services run on designated instance types and scale independently via `bentoml.depends` [6]. This is architecturally relevant for ensemble models—each model (XGBoost, LightGBM, neural network) can be a separate BentoML service. BentoML supports adaptive batching, containerization, and multi-modal inference graphs [6]. Deployment is streamlined to a single command (`bentoml deploy .`) targeting BentoCloud [6]. It supports pandas DataFrames, numpy arrays, and PyTorch tensors natively as I/O types [6].

**BentoML's main architectural limitation** for this use case is that it is not Kubernetes-native in the same operational sense as KServe or Seldon—while Bentos can be deployed to Kubernetes, the operational primitives (autoscaling, canary rollouts, drift detection) are either BentoCloud-managed or require custom implementation.

## 2. Inference Latency (p95, p99)

**No public p95/p99 latency benchmarks directly comparing these four platforms were found.** This is a significant gap in published research. However, architectural analysis provides directional guidance:

| Platform | Expected Latency Profile | Rationale |
|----------|------------------------|-----------|
| **Seldon + Triton FIL** | **Lowest expected** | FIL backend is GPU-accelerated for tree models; TensorRT for neural nets; dynamic batching optimizes GPU utilization; gRPC endpoints minimize serialization overhead |
| **KServe** | **Low-Medium** | Model caching reduces cold starts; supports GPU inference; overhead from Kubernetes CRD abstraction layer; InferenceGraph adds routing hops |
| **Ray Serve** | **Low-Medium** | Dynamic request batching built-in; fractional GPU sharing; in-process model calls avoid network hops for ensembles; but Ray actor overhead adds latency |
| **BentoML** | **Medium** | Adaptive batching helps throughput; Python-based serving layer; no native GPU-accelerated tree model backend equivalent to FIL |

For a 50M daily transaction system (~580 TPS average, ~5,800 TPS at 10x burst), sub-100ms p99 latency is typically required. Triton's FIL backend with dynamic batching is architecturally best positioned to deliver this, especially on GPU infrastructure where tree inference can be 10-40x faster than CPU [5].

## 3. Throughput Under Burst Traffic (10x Normal Load)

At 50M daily transactions, normal load is approximately **580 TPS**, meaning 10x burst reaches **~5,800 TPS**. All four platforms claim autoscaling capabilities, but with different mechanisms:

- **Seldon Core 2**: Dynamic auto-scaling with multi-model serving (MMS) and resource overcommit. Scales to zero for on-demand workloads with state preservation [1]. Triton's dynamic batching (up to batch size 32,768) is specifically designed to absorb traffic spikes by accumulating requests into optimal batch sizes [5].

- **Ray Serve**: Built on Ray's distributed scheduler, enabling horizontal scaling across machines. Request-based autoscaling adjusts the number of replicas [2]. The fractional GPU model allows packing more model replicas per GPU during burst periods.

- **KServe**: Request-based autoscaling (built on Knative), tailored for both predictive and generative patterns. Includes scale-to-zero for cost optimization [3]. Knative's autoscaler reacts to concurrency metrics but can have 10-60 second scaling lag during sudden bursts.

- **BentoML**: Services scale independently based on demand. Adaptive batching groups requests for throughput optimization [6]. BentoCloud provides managed autoscaling.

**Key concern**: Kubernetes-based autoscaling (KServe, Seldon) has inherent cold-start latency when spawning new pods (10-30+ seconds for model loading). Ray Serve can pre-warm workers faster since models are loaded in existing Ray cluster nodes. For 10x bursts, **pre-provisioned capacity with dynamic batching** (Triton) is more reliable than reactive autoscaling.

## 4. A/B Testing for Model Variants

| Platform | A/B Testing Support | Mechanism |
|----------|-------------------|-----------|
| **KServe** | **Built-in** | Canary rollouts and traffic splitting via InferenceService CRD; native A/B testing through Control Plane [3] |
| **Seldon Core 2** | **Built-in** | Customizable pipeline with built-in traffic splitting; supports canary and mirror deployments [1] |
| **Ray Serve** | **Custom implementation required** | Must implement traffic routing logic in Python using Serve handles; no native canary primitive [2] |
| **BentoML** | **Limited/Limited** | No native A/B testing primitives in open-source; BentoCloud may offer traffic splitting (not documented) [6] |

For fraud detection, where A/B testing different model variants (e.g., a new XGBoost feature set vs. the production model) is critical for measuring fraud catch rate without impacting false positive rates, **KServe and Seldon Core 2 have the strongest built-in support**.

## 5. Feature Store Integration Overhead

None of the four platforms provide native feature store integration. All require external feature store systems (e.g., Feast, Tecton, Hopsworks) with the integration overhead falling on the engineering team. However, architectural differences matter:

- **Seldon Core 2**: Explicitly mentions connecting data pipelines, models, and deployment environments, ensuring prediction data is fully auditable [1]. The MLServer ecosystem provides Python extensibility for feature retrieval logic. Integration typically adds **5-15ms** of latency per request for online feature lookups (depending on feature store and network topology).

- **KServe**: Transformer components in the InferenceService pattern can handle feature enrichment before model inference, providing a clean architectural separation [3].

- **Ray Serve**: Feature retrieval can be embedded directly in the Python serving logic, with Ray actors maintaining connections to feature stores—potentially the lowest overhead approach since everything runs in-process [2].

- **BentoML**: Service dependencies (`bentoml.depends`) can model feature retrieval as a separate service, but this introduces inter-service communication overhead [6].

**For 50M daily transactions at 580+ TPS, feature store lookup latency is likely the dominant factor in overall prediction latency**, exceeding model inference time. Pre-computing features or co-locating feature stores with inference services is critical regardless of platform choice.

## 6. Cost Per Million Predictions (Mixed CPU/GPU)

No public cost benchmarks per million predictions were found for any of these platforms. However, cost architecture analysis:

| Platform | Cost Model | GPU Utilization |
|----------|-----------|----------------|
| **Seldon + Triton** | Kubernetes pod costs + GPU node costs; Triton's multi-model per GPU reduces per-prediction cost | **Best**: FIL backend + neural nets share same GPU; dynamic batching maximizes utilization |
| **KServe** | Kubernetes pod costs + GPU node costs; scale-to-zero for idle models | **Good**: GPU acceleration supported; scale-to-zero saves costs during low traffic |
| **Ray Serve** | Ray cluster costs; fractional GPU sharing packs multiple models per GPU | **Good**: Fractional GPU is cost-efficient for multi-model ensembles |
| **BentoML** | Container costs + optional BentoCloud fees; independent service scaling | **Moderate**: No native GPU-optimized tree inference backend |

**Directional estimate** for CPU-only inference on gradient boosting models: $0.05–$0.20 per million predictions on commodity Kubernetes nodes (based on typical cloud pricing). GPU inference via Triton FIL could reduce this by 3-5x for tree models while simultaneously serving neural network models on the same hardware, making **Seldon + Triton the most cost-efficient architecture at scale**.

## 7. Model Versioning & Rollback During Production Incidents

- **KServe**: Model revision tracking is built into the Control Plane. Canary rollouts allow gradual traffic shifting, and rollback is a Kubernetes-level operation (updating the CRD). Rollback can be executed in seconds via `kubectl` [3].

- **Seldon Core 2**: Lifecycle automation enforces best practices for model rollouts. Rollback capabilities minimize deployment risks. Kubernetes-native approach means rollbacks are standard k8s operations [1].

- **Ray Serve**: No built-in versioning or rollback. Requires custom implementation—typically a blue-green deployment pattern with traffic switching via a proxy or load balancer. **This is a significant operational gap for production incident response** [2].

- **BentoML**: Bento packaging provides versioned artifacts. Deployment history is tracked in BentoCloud. Rollback requires redeploying a previous Bento version, which introduces cold-start latency for model loading [6].

**For fraud detection where a bad model deployment can cost millions in missed fraud or false declines in minutes, KServe and Seldon Core 2 offer the fastest, most reliable rollback mechanisms through Kubernetes-native CRD updates.**

## 8. Data Drift Detection & Monitoring

| Platform | Drift Detection | Monitoring |
|----------|----------------|------------|
| **KServe** | **Built-in**: Payload logging, drift detection, outlier detection, adversarial detection. Integrates AI Fairness 360 and ART [3] | Strong native capabilities |
| **Seldon Core 2** | **Built-in via Alibi**: Comprehensive real-time observability split into "operational" and "data science" categories. Alibi provides drift detection, outlier detection, and counterfactual explanations [1] | Strong native capabilities |
| **Ray Serve** | **None**: Requires integration with external monitoring tools (Evidently, WhyLabs, custom Prometheus/Grafana dashboards) [2] | Must be built from scratch |
| **BentoML** | **Limited**: BentoCloud provides some operational metrics; no native drift detection in open-source [6] | Basic metrics only |

For fraud detection where data drift (shifting fraud patterns, new attack vectors, seasonal transaction changes) directly impacts model efficacy, **KServe and Seldon Core 2 are the only platforms with production-grade drift detection built in**.

## 9. Engineering Effort: Initial Deployment vs. Ongoing Maintenance

| Platform | Initial Deployment Effort | Ongoing Maintenance |
|----------|--------------------------|-------------------|
| **Seldon + Triton** | **High**: Requires Kubernetes expertise, Triton configuration, Seldon pipeline definitions, MLServer integration, model format conversion (e.g., XGBoost to FIL format) | **Medium**: Kubernetes operations are well-understood; Seldon handles lifecycle; monitoring built-in |
| **Ray Serve** | **Medium**: Pure Python development lowers initial barrier; Ray cluster setup is simpler than full Kubernetes pipeline | **High**: Custom A/B testing, monitoring, drift detection, versioning all require ongoing engineering investment |
| **KServe** | **High**: Kubernetes CRD expertise required; InferenceGraph configuration; runtime adapter setup for each model framework | **Low-Medium**: Kubernetes-native operations; built-in autoscaling, A/B testing, drift detection reduce ongoing effort |
| **BentoML** | **Low**: Fastest path to serving models; single-command deployment; Python-native | **Medium**: Operational maturity features depend on BentoCloud tier; some features require manual implementation |

**Key insight**: Platforms with higher initial setup cost (Seldon, KServe) provide lower ongoing maintenance burden due to built-in operational features. Ray Serve trades lower setup complexity for significantly higher ongoing operational engineering.

## 10. Cold-Start Latency for New Model Deployments

Cold-start latency is critical for fraud detection—during failover events or model updates, every millisecond of model loading time translates to transactions processed without ML protection.

- **KServe**: Explicitly addresses this with **intelligent model caching** that decreases loading times for frequently used models [3]. The model agent caches models locally, reducing cold-start to seconds rather than minutes.

- **Seldon Core 2**: Supports **scale-to-zero with state preservation** for fast cold starts [1]. When combined with Triton, model loading is handled by Triton's model repository, which can pre-load models.

- **Ray Serve**: Cold start depends on Ray cluster initialization and model loading into actor processes. No explicit caching mechanism; relies on Ray's object store and actor lifecycle management [2].

- **BentoML**: Bento images are self-contained Docker containers. Cold start requires pulling the image and loading the model—potentially 30-60+ seconds depending on model size and container registry proximity [6].

## 11. Multi-Framework Operational Complexity

Managing XGBoost, LightGBM, and neural network frameworks simultaneously introduces complexity around model format conversion, dependency management, and unified serving:

- **Seldon + Triton**: **Best separation of concerns**. XGBoost/LightGBM → FIL backend; Neural networks → TensorRT/ONNX Runtime backend. Each optimized independently. Seldon provides unified routing [1][5].

- **KServe**: Each model runs as a separate `InferenceService` with framework-specific runtimes (MLServer for tree models, TFServing/PyTorch for neural networks). InferenceGraph composes them. Clean but requires managing multiple CRDs [3].

- **Ray Serve**: All models run in Python processes within the Ray cluster. Simpler dependency management but potential version conflicts between framework libraries in shared environments [2].

- **BentoML**: Each model is a separate Service. Clean isolation but each service is a separate deployment unit [6].
